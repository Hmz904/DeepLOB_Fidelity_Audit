## Verified: data-pipeline fidelity

The authors' notebooks print the exact number of 100-event windows they train and test on.
That is a checkable claim about the data pipeline alone, independent of any model, so it is
the first thing this audit pins down.

| Split | Author notebook | This repository | Match |
|---|---:|---:|:--:|
| train (first 80% of `Train_..._CF_7`) | 203,701 | 203,701 | ✅ |
| validation (final 20%) | 50,851 | 50,851 | ✅ |
| test (`CF_7` + `CF_8` + `CF_9`) | 139,488 | 139,488 | ✅ |

Underlying event counts: 254,750 training events and 139,587 test events; the chronological
split falls at event 203,800, and each segment loses its first 99 events to the lookback
window.

Reproduce (about a minute, no GPU, roughly 1 GB of disk for the extracted text files):

```bash
python scripts/download_author_setup2.py
deeplob-rep prepare --normalization decimal
DEEPLOB_RUN_REAL_DATA=1 pytest -q tests/test_real_fi2010.py
```

This is a narrow result and is presented as such: it says the windowing, the split boundary
and the label alignment agree with the released code. It says nothing yet about whether the
model reaches the published F1.

## Verified: class balance and the baseline DeepLOB must beat

FI-2010 is strongly imbalanced at short horizons, and the imbalance shrinks as `k` grows.
Any accuracy or weighted-F1 figure is uninterpretable without the floor it sits on.

Test set, 139,488 windows, decimal-precision Setup-2:

| k | up | stationary | down | majority class | majority accuracy | majority weighted F1 | majority macro F1 |
|---:|---:|---:|---:|---|---:|---:|---:|
| 10 | 15.1% | **70.7%** | 14.2% | stationary | 0.7069 | 0.5855 | 0.2761 |
| 20 | 19.7% | **62.1%** | 18.3% | stationary | 0.6208 | 0.4755 | 0.2553 |
| 50 | 27.5% | **47.3%** | 25.2% | stationary | 0.4731 | 0.3039 | 0.2141 |

Regenerate (no training, seconds):

```bash
deeplob-rep dataset-report --horizons 10 20 50 --out-dir results
```

Committed output: `results/fi2010_decimal_class_distribution.csv` and
`results/fi2010_decimal_majority_baseline.csv`.

### What this does to the published numbers

Reading the paper's Setup-2 accuracies against the constant-prediction floor:

| k | paper accuracy | majority accuracy | lift over majority |
|---:|---:|---:|---:|
| 10 | 0.8447 | 0.7069 | **+0.1378** |
| 20 | 0.7485 | 0.6208 | **+0.1277** |
| 50 | 0.8051 | 0.4731 | **+0.3320** |

Two observations worth carrying into the trained-model comparison:

1. At `k = 10`, predicting *stationary* for every window already scores 70.7% accuracy and
   0.586 weighted F1. The headline 0.834 weighted F1 should be read against that floor, not
   against zero.
2. The paper's accuracy is non-monotonic in `k` (84.5 → 74.9 → 80.5), which looks odd until
   the floor is included: the floor falls much faster (0.707 → 0.621 → 0.473) than the
   reported accuracy does, so the *lift* is largest at `k = 50`. Macro F1 is the metric that
   is not distorted by this, which is why it is reported alongside the weighted figures.

This also sets a falsifiable acceptance bar for the pending run below: a replication that
does not clearly beat the majority baseline at every horizon is a failed replication,
whatever its raw accuracy looks like.

## Pending: Ablation Ledger

This is the project's main differentiator. The controlled rows change **one** ambiguous
DeepLOB specification while holding the rest fixed. Whole-profile comparisons are reported
separately because they change several choices at once.

| Choice | Fidelity/reference variant | Counterfactual | Δ weighted F1 | Status |
|---|---|---|---:|---|
| normalization | decimal precision | z-score | — | config included |
| test-time dropout, same checkpoint | on (`author_tf1`) | off via evaluation override | — | config included |
| validation dropout / checkpoint selection | on (`author_tf1`) | off during validation | — | config included; retrains |
| time padding | SAME | VALID | — | config included |
| channel width | 32/64 | 16/32 | — | config included |

The point is not to choose whichever variant gives the highest number. The point is to
estimate the **cost of ambiguity** in the published/released specifications.

### Protocol-level comparison (not a one-factor ablation)

`author_tf1` vs `author_pytorch_literal` changes normalization-adjacent code paths,
BatchNorm, dropout, padding, activations, batch size, optimizer epsilon and checkpoint
semantics together. Its F1 difference is useful as a **specification drift** comparison, but
must not be interpreted as the causal effect of any single choice.

`author_pytorch_literal` vs `author_pytorch_corrected` isolates one thing the released
PyTorch notebook does that no other public implementation appears to have measured: it
applies `softmax` inside `forward()` and passes the resulting probabilities to
`CrossEntropyLoss`. The two configs differ only in that, so their difference is the price of
that bug.

Run the base author-TF1 checkpoint before the evaluation-only dropout counterfactual:

```bash
deeplob-rep run configs/author_tf1.yaml
deeplob-rep run configs/ablations/author_tf1_dropout_off.yaml
deeplob-rep run configs/ablations/author_tf1_validation_dropout_off.yaml
deeplob-rep run configs/ablations/author_tf1_valid_padding.yaml
deeplob-rep run configs/ablations/author_tf1_paper_channels.yaml
# z-score input must first be prepared from the canonical FI-2010 files
deeplob-rep run configs/ablations/author_tf1_zscore.yaml
```

## Inference-dropout uncertainty

The TensorFlow-1 notebook hard-codes dropout as active during prediction. Consequently one
evaluation is one Monte-Carlo dropout draw. The runner stores all raw MC values plus
mean/std/min/max. Two effects are reported separately: **(1) same fitted checkpoint,
test-time dropout on vs off**, and **(2) dropout behavior during validation changing which
epoch is selected**. The first isolates test-time stochasticity; the second measures
protocol/checkpoint-selection drift.

## External reproducibility context

Independent public DeepLOB implementations have reported nontrivial gaps from the original
paper. Those numbers are **context, not directly comparable observations** unless their
preprocessing, horizon definition, metric averaging and split protocol match this
repository. Note in particular that the literature is inconsistent about whether `k` names
the horizon in events (10, 20, 30, 50, 100) or its column index (0–4); this repository
always means the horizon in events. The audit therefore prioritizes its own controlled
protocol comparisons over collecting the highest or lowest number on GitHub.
