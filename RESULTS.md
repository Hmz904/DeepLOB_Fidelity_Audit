## Verified: data-pipeline fidelity

The authors' notebooks print the exact number of 100-event windows they train and test on.
That is a checkable claim about the data pipeline alone, independent of any model, so it is
the first thing this audit pins down.

| Split | Author notebook | This repository | Match |
|---|---:|---:|:--:|
| train (first 80% of `Train_..._CF_7`) | 203,701 | 203,701 | yes |
| validation (final 20%) | 50,851 | 50,851 | yes |
| test (`CF_7` + `CF_8` + `CF_9`) | 139,488 | 139,488 | yes |

Underlying event counts: 254,750 training events and 139,587 test events; the chronological
split falls at event 203,800, and each segment loses its first 99 events to the lookback
window.

Trainable parameter count is 142,691, matching the figure printed by the TF1 notebook and
locked by a unit test.

Reproduce (about a minute, no GPU, roughly 1 GB of disk for the extracted text files):

```bash
python scripts/download_author_setup2.py
deeplob-rep prepare --normalization decimal
DEEPLOB_RUN_REAL_DATA=1 pytest -q tests/test_real_fi2010.py
```

This is a narrow result and is presented as such: it says the windowing, the split boundary
and the label alignment agree with the released code. It says nothing on its own about
whether the model reaches the published F1.

## Verified: class balance and the baseline DeepLOB must beat

FI-2010 is strongly imbalanced at short horizons, and the imbalance shrinks as `k` grows.
Any accuracy or weighted-F1 figure is uninterpretable without the floor it sits on.

Test set, 139,488 windows, decimal-precision Setup-2:

| k | up | stationary | down | majority class | majority accuracy | majority weighted F1 | majority macro F1 |
|---:|---:|---:|---:|---|---:|---:|---:|
| 10 | 15.1% | **70.7%** | 14.2% | stationary | 0.7069 | 0.5855 | 0.2761 |
| 20 | 19.7% | **62.1%** | 18.3% | stationary | 0.6208 | 0.4755 | 0.2553 |
| 50 | 27.5% | **47.3%** | 25.2% | stationary | 0.4731 | 0.3039 | 0.2141 |

Regenerate (no training, seconds):

```bash
deeplob-rep dataset-report --horizons 10 20 50 --out-dir results
```

Committed output: `results/fi2010_decimal_class_distribution.csv` and
`results/fi2010_decimal_majority_baseline.csv`.

### What this does to the published numbers

Reading the paper's Setup-2 accuracies against the constant-prediction floor:

| k | paper accuracy | majority accuracy | lift over majority |
|---:|---:|---:|---:|
| 10 | 0.8447 | 0.7069 | **+0.1378** |
| 20 | 0.7485 | 0.6208 | **+0.1277** |
| 50 | 0.8051 | 0.4731 | **+0.3320** |

Two observations worth carrying into the trained-model comparison:

1. At `k = 10`, predicting *stationary* for every window already scores 70.7% accuracy and
   0.586 weighted F1. The headline 0.834 weighted F1 should be read against that floor, not
   against zero.
2. The paper's accuracy is non-monotonic in `k` (84.5, 74.9, 80.5), which looks odd until
   the floor is included: the floor falls much faster (0.707, 0.621, 0.473) than the
   reported accuracy does, so the *lift* is largest at `k = 50`. Macro F1 is the metric that
   is not distorted by this, which is why it is reported alongside the weighted figures.

This also sets a falsifiable acceptance bar: a replication that does not clearly beat the
majority baseline at every horizon is a failed replication, whatever its raw accuracy looks
like.

The result clears the acceptance bar: weighted F1 exceeds the majority floor by 0.222 and
accuracy exceeds it by 0.113, against the paper's lift of 0.138. The remaining gap to the
published weighted F1 is **2.6 percentage points**.

A replication below the published value is **not** automatically a failed project. The
purpose of this repository is to locate the gap: protocol drift, random seed,
initialization, dropout-at-inference, padding, preprocessing, or a remaining implementation
mismatch. With one seed and one horizon, none of those has been isolated yet, and the
Ablation Ledger below is how that work is done. The honest statement today is that an
independent reimplementation built only from the paper and the released notebook lands
2.6 points short, and the cause is not yet attributed.

throughput-bound on the convolutions.

### Determinism, verified the hard way

The first attempt at this run was killed at 75 minutes by a forced Windows update reboot. It
had written a `.partial` checkpoint at **epoch 69, validation loss 0.6693622545938956**.

The completed rerun, from the same seed on a rebooted machine, selected **epoch 69 with
validation loss 0.669362**. Same epoch, same loss to every printed digit.

This is stronger evidence for the determinism machinery than any unit test in the
repository: two independent process lifetimes, separated by a full operating-system restart,
followed a bit-identical optimisation trajectory for 69 epochs.

The caveat in `FIDELITY.md` still stands unchanged — this says nothing about bit identity
across GPU architectures, CUDA releases, or TensorFlow versus PyTorch kernels.

### Test-time dropout noise is small

The TF1 protocol keeps dropout active at prediction, so one evaluation is one Monte-Carlo
draw. Five draws on the fitted k=10 checkpoint:

| | mean | std | min | max |
|---|---:|---:|---:|---:|
| weighted F1 | 0.807569 | **0.000213** | 0.807268 | 0.807786 |
| accuracy | 0.819583 | 0.000223 | 0.819260 | 0.819769 |

Test-time stochasticity contributes about **±0.02 percentage points** of weighted F1, two
orders of magnitude below the 2.6-point gap to the paper. Reporting a single draw is
therefore not materially misleading at this horizon — but this is the measurement that
licenses that statement, and it was not knowable in advance.

This covers only effect (1) of the two separated in `FIDELITY.md`: same fitted checkpoint,
dropout on. Effect (2), dropout disabled during validation changing which epoch is selected,
requires the retraining ablation and is still pending.

An early two-epoch smoke run produced a standard deviation of **exactly 0.0** across the
same five draws, together with weighted F1 of 0.585495 — the majority baseline to six
decimal places. An undertrained model that predicts one class with large margins is immune
to 20% dropout noise. The zero was a symptom of collapse, not a broken MC implementation,
and the distinction was only resolvable by training to convergence.

## Pending: Ablation Ledger

This is the project's main differentiator. The controlled rows change **one** ambiguous
DeepLOB specification while holding the rest fixed. Whole-profile comparisons are reported
separately because they change several choices at once.

| Choice | Fidelity/reference variant | Counterfactual | delta weighted F1 | Status |
|---|---|---|---:|---|
| normalization | decimal precision | z-score | — | config included |
| test-time dropout, same checkpoint | on (`author_tf1`) | off via evaluation override | — | config included |
| validation dropout / checkpoint selection | on (`author_tf1`) | off during validation | — | config included; retrains |
| time padding | SAME | VALID | — | config included |
| channel width | 32/64 | 16/32 | — | config included |

The point is not to choose whichever variant gives the highest number. The point is to
estimate the **cost of ambiguity** in the published/released specifications.

### Protocol-level comparison (not a one-factor ablation)

`author_tf1` vs `author_pytorch_literal` changes normalization-adjacent code paths,
BatchNorm, dropout, padding, activations, batch size, optimizer epsilon and checkpoint
semantics together. Its F1 difference is useful as a **specification drift** comparison, but
must not be interpreted as the causal effect of any single choice.

`author_pytorch_literal` vs `author_pytorch_corrected` isolates one thing the released
PyTorch notebook does that no other public implementation appears to have measured: it
applies `softmax` inside `forward()` and passes the resulting probabilities to
`CrossEntropyLoss`. The two configs differ only in that, so their difference is the price of
that bug.

The base `author_tf1` k=10 checkpoint required by the evaluation-only dropout counterfactual
now exists, so that row can be filled without retraining.

```bash
deeplob-rep run configs/ablations/author_tf1_dropout_off.yaml
deeplob-rep run configs/ablations/author_tf1_validation_dropout_off.yaml
deeplob-rep run configs/ablations/author_tf1_valid_padding.yaml
deeplob-rep run configs/ablations/author_tf1_paper_channels.yaml
# z-score input must first be prepared from the canonical FI-2010 files
deeplob-rep run configs/ablations/author_tf1_zscore.yaml
```

## Defects found by executing the pipeline

Three of these are in this repository and are logged here rather than in `FIDELITY.md`,
which documents fidelity to the published specification rather than implementation quality.

**`patience` is a dead parameter.** The `author_tf1` profile carries `patience: 20` alongside
`early_stopping: False`, so the run always executes all 200 epochs. On this run the best
validation loss occurred at **epoch 69**; epochs 70 through 200 produced no improvement and
consumed **2.4 hours** with no effect on the selected checkpoint. Because checkpoint
selection is by best validation loss, enabling early stopping with the profile's own
patience would have stopped at epoch 89 and selected **the identical weights and identical
metrics**. This is not a fidelity trade-off, it is unspent compute — but it should be enabled
with a widened patience and recorded in `FIDELITY.md` as a compute bound, since k=20 and
k=50 are not guaranteed to converge as early.

**No per-epoch progress output.** A 3.5-hour training run prints nothing between start and
finish. During the interrupted attempt there was no way to distinguish a live process from a
hung one except by inspecting GPU utilisation, and no training curve survives the run. The
convergence claim above rests on two checkpoint snapshots rather than a loss trajectory.

**No resume.** `train.py` writes a `.partial` checkpoint on validation improvement but stores
no optimizer or RNG state and offers no `--resume`, so the forced reboot cost the full 75
minutes. The `.partial` file did preserve the epoch-69 weights, which is what made the
determinism check above possible.

**Text I/O without explicit encoding (portability).** Six call sites use `Path.read_text()`
or `write_text()` without `encoding="utf-8"`, which resolves to the system locale. On a
Chinese Windows install the locale is GBK and any non-ASCII byte raises
`UnicodeDecodeError`; `tests/test_dataset_report.py` fails on the first curly quote in
`CHANGELOG.md`. Linux CI is UTF-8 and never reproduces it. One of the six is
`runner.py`'s `ast.parse(path.read_text())` in the code-fingerprint path, which would abort a
completed training run at the moment it writes its manifest — the most expensive possible
place to fail.

## Inference-dropout uncertainty

The TensorFlow-1 notebook hard-codes dropout as active during prediction. Consequently one
evaluation is one Monte-Carlo dropout draw. The runner stores all raw MC values plus
mean/std/min/max. Two effects are reported separately: **(1) same fitted checkpoint,
test-time dropout on vs off**, and **(2) dropout behavior during validation changing which
epoch is selected**. The first isolates test-time stochasticity; the second measures
protocol/checkpoint-selection drift. Effect (1)'s magnitude is now measured for k=10 above;
effect (2) is pending.

## External reproducibility context

Independent public DeepLOB implementations have reported nontrivial gaps from the original
paper. Those numbers are **context, not directly comparable observations** unless their
preprocessing, horizon definition, metric averaging and split protocol match this
repository. Note in particular that the literature is inconsistent about whether `k` names
the horizon in events (10, 20, 30, 50, 100) or its column index (0-4); this repository
always means the horizon in events. The audit therefore prioritizes its own controlled
protocol comparisons over collecting the highest or lowest number on GitHub.
